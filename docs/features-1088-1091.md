# 1088-1091: reel analytics, safe delete, DM replies, performance

Built on the Next 15 branch (`outly-next15`). No new dependencies, no rewrite.

## 1088 Reel analytics popup (Content)

- A card that is live on at least one platform opens **ReelAnalytics** (`components/content/ReelAnalytics.tsx`).
  Drafts, scheduled and failed posts still open the post sheet. "Details and actions" in the popup leads on to it.
- Data: `GET /api/posts/:id/insights` (`app/api/posts/[id]/insights/route.ts`, `lib/insights/post.ts`).
  - Ownership through `ownedPost` (another workspace gets 404). Tokens are decrypted server side only and never logged or returned.
  - Cache: `insights:<userId>:<postId>`, 2 minutes, single-flight per server instance. `?fresh=1` (Refresh button)
    re-fetches only when the held numbers are 30 s or older, and is limited to 12 per user per minute.
  - The popup shows "Updated N min ago" and, per platform, "Fetched N min ago". Nothing is labelled "live".
  - Each fetch also stores a TargetMetric increment (live total minus what is stored, at most every 30 minutes),
    so card view counts and Analytics agree with the platform.
- Metrics per platform (real API data only, never estimated):

| Metric | Instagram | YouTube | Facebook |
|---|---|---|---|
| Views | yes | yes | yes (Reels plays) |
| Reach | yes | not offered | yes |
| Likes / comments | yes | yes (null when hidden or off) | yes |
| Shares | yes | YouTube Analytics (1 to 2 days behind) | not offered per reel |
| Saves | yes | not offered | not offered |
| Avg watch time / watch time | Reels only | YouTube Analytics (1 to 2 days behind) | yes |
| Impressions | deprecated by Meta (views replaced it) | not offered | not offered |
| Engagement rate | (likes+comments+shares+saves) / reach, % | (likes+comments+shares) / views, % | (likes+comments) / reach, % |

  Metrics a platform could give but did not are listed as "Not available for this post". X, TikTok, Threads and
  LinkedIn say "not available yet" instead of showing numbers. Practice posts say so and show none.
- Errors read plainly: reconnect (expired token), missing permission, rate limited, network, removed on the platform.

## 1089 Delete, synced with the platforms

`DELETE /api/posts/:id` (`lib/posts/delete.ts`).

1. Scheduled or still waiting/uploading: every destination not yet handed to its platform is marked
   `failed / CANCELED` first, then the post is removed. Workers check that marker before each step and find no row
   afterwards, so a booked post cannot go out after it was deleted.
2. A platform is already processing it: refused with `IN_FLIGHT` (it cannot be called back); everything else is stopped.
3. Live: platform deletes happen only with `?platforms=1` after the creator confirmed in the sheet. If any platform
   delete fails, the post stays in Outlly (`REMOVE_FAILED`) so its links are not lost.
4. Duplicate requests (double click, two tabs) share one in-flight answer; a later one returns `already_gone`, not an error.
5. Editors cannot delete on platforms. Members limited to some accounts cannot delete others' posts.

**Not supported by the platforms' APIs:** Instagram and TikTok posts cannot be deleted by API. The creator is asked to
acknowledge this; the result lists them as "delete in the app" with the link.

## 1090 Direct message replies

Why the reply box was missing: the composer only rendered inside Meta's 24-hour window, and the page itself scrolled
so the box could sit below the fold on long threads. In addition, Instagram's conversations API can list our own
account under an id other than the `user_id` stored at connect; matching by id only could treat our own side as
"the person", which flips every message and keeps the window shut.

Changes:
- The composer is always there. When it cannot send it is disabled and says why: editor, reconnect needed, messaging
  switched off until Meta approves it, or the 24-hour window closed (with a link to answer in the app).
  `ThreadView.replyBlock` carries the reason from the server (`replyBlockFor`, the same checks the send path makes).
- The thread pane has a fixed height; messages scroll inside it, so the box stays on screen.
- Self is recognised by id or username; message direction is decided by the other person's id.
- Sending: an optimistic bubble shows "Sending...", becomes a real message only after the server confirms Meta took
  it, and shows "Not sent" with Retry / Edit on failure. Nothing is ever shown as sent when it was not.
- Idempotency: the browser sends a `clientId`; repeats of the same send share the first attempt
  (`sendOnce`, 10 minutes, failures forgotten so Retry works). After a send the thread is reloaded.

**Not supported:** replies after 24 hours (Meta's human-agent tag needs a separate approval Outlly does not have);
attachments in replies; per-instance dedupe only (see Limits).

## 1091 Performance

- Content library: 48 posts per page with a stable cursor (`updatedAt desc, id desc`) and "Show more"
  (`GET /api/posts?library=1&cursor=`). Before: 200 posts, every review and signed media URL, and a views sum
  over every target the workspace ever had on each visit. Tab counts now come from one `groupBy`.
- Views are summed only for the targets on the page (`TargetMetric` is indexed by `targetId`).
- New index `Post(userId, updatedAt)` (applied by `scripts/db-sync.mjs` on deploy; also in `schema.template.prisma`).
- Inbox: the practice-thread seed check no longer runs on every 30 s poll for users already seeded.
- Already in place and kept: `/api/files` `private, max-age=3600`; brand/sample art `public, s-maxage=604800`;
  Prisma pool `connection_limit>=3`, `pool_timeout>=20` on Vercel.

### Load test (localhost only, 2026-11-02)

Setup: production build (`next start`, one Node process), SQLite, 100 seeded test users (`@load.test`, practice
Instagram accounts; one with 200 posts, the rest 60). 100 virtual users, 10 s ramp, 60 s steady, each looping
Content page, library page 1 and 2, reel insights, inbox list, one thread, Calendar page, then 0.5 to 1.5 s pause.
Scripts were kept out of the repo and deleted afterwards.

| Content page (HTML) | 655 | 3526 | 7058 | 7794 | 0 |
| Library page 1 | 655 | 232 | 783 | 1191 | 0 |
| Library page 2 (cursor) | 655 | 273 | 1176 | 1342 | 0 |
| Reel insights | 655 | 158 | 527 | 629 | 0 |

Total 4585 requests in 72 s (63.6 req/s), error rate 0%. Insights served from cache 84.7% of the time.

Database work for the Content page, before vs after (same data, 100 concurrent loads, `bench.ts`):

| Case | Before p50 / p95 | After p50 / p95 | Posts per load |
|---|---|---|---|
| 100 different users | 2162 / 3503 ms | 237 / 238 ms | 60 to 48 |
| One user with 200 posts, x100 | 2086 / 3454 ms | 137 / 138 ms | 200 to 48 |

Findings:
- **Per-IP rate limit.** The first run returned 38% `429`s because every virtual user came from one address and
  `route()` limited by IP before sign-in. The second run gave each user its own forwarded IP. In production a team
  behind one office network or carrier NAT shared that limit. Fixed in 1092, below.

## 1092 Per-user rate limits

`lib/http.ts` `route()`:
- Public routes (sign-in, sign-up, codes) and requests without a session cookie: per IP at the route's limit, as before.
- Signed-in routes: per user at the route's limit, plus a per-IP ceiling 10x higher (`IP_CEILING_X`) under its own key.
- A session cookie that fails to verify is charged to the plain per-IP budget, so a made-up cookie gains nothing.
- Tests: `tests/round-1092-ratelimit.test.ts`.
- **Page render time.** Content and Calendar pages sit around 3.5 s p50 under this load, and Calendar was not touched,
  so the remaining cost is server rendering in a single Node process (CPU bound), not the database. On Vercel each
  request scales across instances; a staging run is needed to measure that.

## Independent review (11-02) and what changed

No high-severity or security findings. Fixed after review:
- Backfilled DMs with no sender are skipped (logged) instead of counted as inbound, so they cannot re-open the 24-hour window.
- Content tabs page through their own posts (`?library=1&status=`), so a tab whose posts are not on the first "All" page
  loads them instead of showing an empty grid next to a non-zero count.
- Stored view totals follow downward corrections by the platform (signed increments; metrics missing from an answer are left alone).
- The engagement-rate note names only the metrics that were actually divided.
- A refresh over the limit says "Refresh limit reached" instead of looking like it refreshed.
- DM sync problems send only the error code to the browser; the platform's raw error stays in the server log.

Kept on purpose: when a delete is refused (`IN_FLIGHT`, `REMOVE_FAILED`), destinations not yet sent stay stopped.
The creator asked for the post to go, so it is safer that nothing more publishes; the message says so.

## Limits and follow-ups

- Caches and dedupe maps (`lib/cache.ts`, `sendOnce`, delete in-flight map) are per server instance. On Vercel with
  several instances a duplicate can slip through between instances; Upstash (already planned) would make them shared.
- The local load test uses SQLite and one Node process. It shows the app's own overhead and relative gains, not
  production capacity, which depends on the Postgres pooler and Vercel concurrency. A staging run is needed before
  any capacity claim; never point the load script at production (it refuses non-localhost URLs).
